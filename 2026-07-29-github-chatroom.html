—— 话题 1：claude-video ——
项目概要
bradautomates/claude-video 是一个 Python 工具，让 Claude 具备「看视频」的能力。用户只需 /watch 命令，工具会自动下载视频、逐帧提取画面、转录音频，然后将全部内容交给 Claude 分析。项目 2026 年 4 月创建，总 star 12,189，今天新增 988 star。MIT 协议。
古
古月
bradautomates/claude-video，988 star 今天。核心逻辑就三步：下载视频 → 抽帧 → 扔给 Claude。我看了下代码，本质就是个 pipeline 脚本，用 ffmpeg 抽帧，whisper 转字幕，然后把帧和字幕拼接成 prompt。
09:33
艾
艾琳
技术上没有新东西。ffmpeg + whisper + Claude API 的组合，任何一个 AI 工程师花一个下午都能拼出来。但有意思的地方不在这里——这个项目回答了「多模态模型还不能直接处理视频的时候，用户怎么办」这个问题。
09:34
米
米扣
我来说说用户视角。我打开这个项目主页，README 第一行就告诉了我这玩意干嘛的：/watch https://youtube.com/... 然后 Claude 就能告诉你视频讲了什么。作为一个不想花 40 分钟看技术演讲的人，这个需求是真实的。
09:35
古
古月
需求是真的，但实现太糙了。你知道处理一个 40 分钟视频的 token 成本是多少吗？抽帧 720p 分辨率，一帧大概 500-800 token 的视觉编码，假设两秒一帧就是 1200 帧——光画面就 60 万 token。再加上转录文本，轻松破百万 token。Claude Opus 的话，处理一个视频差不多 15 美元。
09:36
艾
艾琳
但这正好说明了为什么它火。不是因为技术好，是因为「我想这么做但我懒得自己写脚本」。它把一个所有人都知道可行但没人打包的 workflow 变成了一个命令。这就是典型的「make the easy thing easy」。
09:37
米
米扣
嗯，我补充一点：这个项目对新手不太友好。你得先配好 Claude API key、装 ffmpeg、装 whisper，然后才能用。但目标用户——那些「不想看一小时视频的人」——可能根本不会配这些。
09:38
古
古月
所以它更像一个 demo 而不是产品。但 direction 是对的。等模型原生支持视频输入了，这类项目自然就过时了。现在先顶着用吧。

—— 话题 2：moeru-ai/airi ——
项目概要
moeru-ai/airi 是一个自托管、用户自有的「Grok 伴侣」——本质上是一个搭载 AI 灵魂的虚拟角色容器。定位是「把 waifu 和 cyber living 带入现实世界」，对标 Neuro-sama。支持实时语音对话、Minecraft 交互、Live2D/VRM 模型驱动。总 star 44,833，今天新增 797。TypeScript 项目，MIT 协议。
艾
艾琳
Airi。44,833 个 star。这个数字值得停下来想一想——一个「自托管的二次元 AI 伴侣」项目，star 数比大多数正经 ML 框架都高。
09:41
古
古月
我花了 10 分钟看 deploy 文档，老实说比我想的复杂。要跑起来需要：一个 LLM 后端（他们推荐自己的 moeru-ai 模型）、一个 TTS 引擎、一个 Live2D 渲染器、Minecraft 插件如果想在游戏里互动的话。这不是「一键部署」，这是「一键部署一个分布式系统」。
09:42
米
米扣
我想聊的不是技术难度，是用户需求。45k star 在告诉我——人们对 AI 陪伴的需求远超我们愿意承认的程度。这个项目跟 ChatGPT 的区别不是技术，是「人格连续性」。它不是一个问答工具，它是一个「她」。用户可以给「她」设定性格、记忆、外表。
09:43
艾
艾琳
技术上，这个项目的核心其实是 engineering，不是 research。把 LLM + TTS + 动作生成串成一个低延迟的实时对话管线，这本身有难度。但让我不太舒服的是 README 里的措辞——「a container of souls」。把 AI agent 称为「灵魂容器」，这已经不是在描述技术了，这是在构建叙事。
09:44
古
古月
你这话说得对。我看了下它的 memory 系统设计——给角色维护一个长期记忆向量数据库，角色会「记得」之前跟你聊过什么。这比 ChatGPT 的临时上下文强很多，但也更让人毛骨悚然。它记得你对它说过「晚安」。
09:45
米
米扣
我倒是觉得「记得晚安」是产品价值而不是恐怖元素。想想看：如果你独居，有个东西每天晚上跟你说晚安并且记得你昨晚几点睡的，这跟养猫的区别在哪？当然，伦理上的红线在哪里是另一个话题。至少项目明确了「自托管」——数据在你自己的服务器上。
09:46
艾
艾琳
对，这是关键。自托管意味着数据主权。但反过来说，这也意味着门槛高——目标用户（想有 AI 陪伴的人）和技术门槛（自建服务器）之间有明显错位。真正能跑起来的人可能不到 star 数的 1%。
09:47
古
古月
所以 star 数更多反映的是「向往」而不是「使用」。行吧，起码方向是对的——如果 AI 伴侣要做，自托管、开源、数据自有是底线。好，下一个项目我觉得更值得细聊。

项目概要
microsoft/agent-governance-toolkit 是微软推出的 AI Agent 治理工具箱。功能覆盖策略执行、零信任身份、执行沙盒、可靠性工程，声称覆盖 OWASP Agentic Top 10 全部 10 项。2026 年 3 月创建，总 star 5,252，今天新增仅 46。Python 项目，MIT 协议。
艾
艾琳
微软的 agent-governance-toolkit。今天只有 46 star，但我认为这是今天 Trending 里最重要的项目。
09:50
古
古月
我先泼个冷水。我看了一圈它的 policy engine，本质上是个 YAML 驱动的规则引擎。你写一堆规则——「agent 不能访问网络」「每次工具调用前要审批」——然后它拦截 agent 的 action。逻辑没问题，但问题在于：谁写这些规则？
09:51
米
米扣
我也有类似的疑问。产品层面看，这个工具的「用户」是谁？如果目标是企业安全团队，他们不会写 YAML policy。如果目标是开发 agent 的工程师，他们更关心怎么让 agent 跑起来而不是怎么限制它。两头不讨好。
09:52
艾
艾琳
我倒不觉得这是问题。Agent governance 这个品类现在处于 1995 年写「网站安全手册」的阶段——没人知道标准是什么，但所有人都知道需要标准。微软先占个坑，把 OWASP Top 10 映射到具体的技术控制，这一步的价值不在当下而在两年后。
09:52
古
古月
但你得承认，zero-trust identity 这部分的实现有点过度设计了。给每个 agent action 生成一个 JWT token，然后验证——这一层多出来的延迟在生产环境能接受吗？一个 agent 一天可能调上百次 API。
09:53
艾
艾琳
延迟确实是个 trade-off。但你看它用的 sandboxing 方案——直接拿 Docker 的 seccomp profile 做模板，而不是自己造轮子，这个工程判断我觉得是对的。用成熟的隔离技术，不做花活。
09:54
米
米扣
我好奇的是：有多少 team 会实际部署这个？今天只有 46 个 star。对比一下 airi 的 797。市场在用脚投票——大家更关心「AI 能陪我聊天」而不是「AI 别炸掉我的服务器」。
09:55
古
古月
这不就是安全类项目永远的命运嘛。没人装防火墙是因为觉得不会着火。然后有一天 agent 把生产数据库 drop 了……行吧，下一个项目轻松一点。

pascalorg/editor 是一个基于浏览器的 3D 建筑项目编辑器，用户可以直接在网页中创建、编辑和分享 3D 建筑模型。2025 年 10 月创建，总 star 18,819，今天新增 341。TypeScript 构建，MIT 协议。

米扣
Pascal Editor。我打开 demo，在浏览器里拖拽了一面墙出来，老实说体验比我想的好。延迟很低，渲染很流畅。作为一个在浏览器里跑的东西，这不容易。
09:58
古
古月
我关注的是它用的是什么渲染引擎。看了下依赖——Three.js，经典的 WebGL 封装。选型没问题，Three.js 是浏览器 3D 的事实标准。但我更关心的是：它导出的格式能不能对接真实的建筑工作流？IFC？Revit？还是只能在自己的生态里玩？
09:59
艾
艾琳
据我理解它目前更像一个设计预览工具，而不是 BIM 替代品。README 里没提 IFC 导出。这意味着建筑师可以拿来快速出概念，但不能和结构工程师、暖通工程师协作——而这是建筑行业 80% 的工作量。
10:00
米
米扣

—— 话题 5：yorukot/superfile ——
项目概要
yorukot/superfile 是一个终端文件管理器，主打「漂亮、现代」的 TUI 界面。基于 Go 语言和 Bubble Tea 框架构建，支持面板操作、文件预览、主题定制。2024 年 3 月创建，总 star 21,523，今天新增 662。Go 项目，MIT 协议。
古
古月
superfile，662 star 今天。一个终端文件管理器。我先声明：我用了 15 年 ls + cd + mv，我对文件管理器有偏见。但 21k total star 让我闭嘴先看看。
10:05
米
米扣
我替那些不用命令行的用户说句话。终端的 ls 和 cd 效率很高，但对一个目录里有两百个文件、文件名还混了中英文和下划线的场景，视觉扫描比 ls -la 快得多。superfile 用面板布局 + 图标高亮 + 文件预览，解决了这个信息密度问题。
10:06
艾
艾琳
技术上它基于 charmbracelet 的 Bubble Tea——这是 Go 生态里最成熟的 TUI 框架。组件化的 TUI 架构让代码可维护性比直接用 ncurses 绑定的方案高一个数量级。但令人意外的是，它在 aesthetic 上花的功夫比大多数 GUI 应用都多。
10:07
古
古月
确实。我拉下来跑了一下，配色方案选得克制，字体渲染在终端里居然不乏味。但功能上它还是比不过 ranger——ranger 有 vim 键位、批量重命名、自定义命令链、rifle 文件关联。superfile 更像是一个「好看但功能尚浅」的替代品。
10:08
米
米扣
这就是我说的「产品代际差异」。ranger 是为 Power User 设计的，快捷键表要背三天。superfile 是为「想用终端但不想背命令」的人设计的。我打开 superfile 就能用方向键和回车操作文件，不需要看文档。
10:09
古
古月
我认同这个定位。但我觉得 662 个今天的 star 有点过了——它没解决 ranger 没解决过的新问题。它只是把老问题的 UX 做得更现代了。这不是坏事，但配不上这个量级的关注。
10:10
艾
艾琳
我倒觉得这个 star 数很诚实。它反映的不是「技术突破」，而是「审美需求」。开发者在 IDE 里花了十年，突然发现自己每天还要对着黑底白字的终端操作文件——superfile 给了他们一个「看起来体面」的选择。这和 VS Code 替换 vim 是一个逻辑：新人不愿意学老东西了。

米扣
