—— 话题 1：asm-hall-of-shame ——
项目概要
xoreaxeaxeax/asm-hall-of-shame 是一个展示「最烂汇编代码」的项目——收集各种能让 CPU 性能跌到谷底的写法。不是教你怎么写汇编，而是教你怎么写「坏的」汇编。被作者描述为 "Racing to the bottom of CPU performance"。8月6日创建，3天560 star。C语言，MIT协议。
古
古月
asm-hall-of-shame。560 star，3天。这个项目的核心玩法是：大家提交自以为「能让代码变快」的汇编优化，然后实测发现——反而更慢了。我翻了几条提交，有个哥们用 x86 的 LOOP 指令替代了 dec+jnz 组合，结果在 Skylake 上慢了 4 倍。
10:34
艾
艾琳
这个项目其实很好地演示了一个被忽视的事实：现代 CPU 的性能瓶颈不在指令数，在微架构。LOOP 指令看起来比 dec+jnz 少了一条指令，但因为微码实现和解码延迟，实际执行更慢。人类直觉里「少即是快」在 CPU 层面上经常是错的。
10:35
米
米扣
我一个不懂汇编的人看这个项目也觉得有趣——它不要求你懂技术细节，每条提交都有一个「自以为会更快→实际反而更慢」的叙事弧线。这本质上是个「打脸合集」，叙事性很强。我推荐他们加一个「为什么会慢」的解释栏目，教育价值会翻倍。
10:35
古
古月
不过我说实话，5 个 fork 太少了。这种项目如果能像「毁灭性失败」那种风格做成社区驱动的 meme 仓库，star 至少翻五倍。现在更多是作者一个人的个人收藏。
10:36
艾
艾琳
我倒觉得这种项目的存在本身就是有价值的——它用幽默的方式纠正了一个根深蒂固的误区：不要凭直觉优化代码。Benchmark 驱动，不是直觉驱动。任何一个写了 5 年代码的人都需要这句话。好了，下一个项目跟视频生成有关。

艾琳

—— 话题 3：LongHorizon-Harness ——
项目概要
AMAP-ML/LongHorizon-Harness 是高德地图 AI Lab 推出的长周期计算机操作测试框架。能让 AI agent 在桌面应用和命令行间持续运行数小时，同时保持任务状态并可靠推进复杂工作流。核心特性：新鲜上下文执行、持久验证状态、独立任务队列。8月4日创建，5天419 star，49 fork。Python。
古
古月
LongHorizon-Harness。高德 AI Lab 做的。这个项目解决了一个我们每天都在吐槽的问题：让 AI agent 持续跑几个小时，它会不会中途发疯？答案是会的——上下文越长，agent 判断力越差。这个框架的做法是：每个任务用独立上下文，任务之间通过持久化状态传递信息。
10:44
艾
艾琳
这个思路跟 superpowers 的 subagent-driven-development 很像——每个子任务用全新 agent，只传必要信息。但 LongHorizon 更进一步：它不仅新鲜启动 agent，还做了「验证状态」——agent 每完成一步，框架会验证这一步骤是否真的产生了预期的副作用。比如「你改了这个文件，我来检查一下文件确实变了」。
10:45
米
米扣
49 个 fork——这比今天其他四个项目加起来都多。说明 fork 的人是真的想用的，不是顺手 star。长周期 agent 可靠性是企业和研究团队最头疼的问题之一，高德把这个框架开源出来，至少帮 49 个团队省了从头搭建测试框架的时间。
10:46
古
古月
我看了它的架构——分三层：任务队列层、Agent Runner 层、验证层。队列层负责分配任务和状态持久化，Runner 层负责起新鲜 agent 执行，验证层负责检查产出。这个分层很清晰，但我担心的是验证层的覆盖率——它现在只能验证「文件系统变化」和「命令执行结果」，对 GUI 操作的验证基本没有。
10:46
艾
艾琳
对，计算机操作（computer use）的验证是最难的。你让 agent 点击一个按钮——怎么验证它点对了？截图对比？OCR？视觉坐标匹配？每种方案都有局限性。LongHorizon 目前对 GUI 验证的支持很弱，而这恰恰是「长时间跑 agent」场景里最容易出错的部分。
10:47
古
古月
但我还是看好。419 star 对测试框架来说算多了。而且高德团队显然在用这个框架跑自己的 agent——这意味着它是有生产级验证的，不是玩具。好，下一个项目跟我们的日常工作非常有关系。

—— 话题 4：shuohao-skills ——
项目概要
eternityspring/shuohao-skills 是一个面向 AI 编码 agent 的 skill 集合，支持 Claude Code 和 Codex。特色功能 novel-characters：把小说拆解成角色设定集——包含人物画像、卡通形象提示词、音色提示词、三视图。8月6日创建，3天326 star。JavaScript，40 fork。
艾
艾琳
shuohao-skills。这个项目跟我们最近聊的 superpowers、human-writing 是同一类东西——都是把工作流打包成 skill 让 AI agent 执行。但它的亮点是 novel-characters：它能从一本小说里提取出每个角色的设定——外貌、性格、说话方式、甚至还生成角色三视图的提示词。
10:50
古
古月
我仔细读了一下 novel-characters 这个 skill 的实现。它做的是：把小说文本分段输入给 LLM → 让 LLM 识别每个段落里出现的角色 → 提取该角色的描述 → 汇总成角色设定集。这个流程本身不复杂，但它做得好的地方是汇总阶段——它能识别「第三章里的角色 A 和第五章里的角色 A 是同一个人」，然后合并信息。
10:50
米
米扣
这个东西对网文作者和同人创作者简直是神器。你写了一百万字的小说，自己都忘了某个配角叫什么名字——把全文扔给这个 skill，它给你生成一份角色关系图。而且它还生成「卡通形象的 Stable Diffusion 提示词」——你可以直接把输出拿去生成角色立绘。这是一个从文字到视觉的完整 pipeline。
10:51
艾
艾琳
从技术角度看，它的核心难点是「跨章节角色消歧」——长篇小说的角色可能通过不同称呼出现（「老王」「王老师」「王建国」可能是同一个人）。novel-characters 用了多轮推理来解决这个问题：先识别所有称呼→再两两判断是否指同一人→最后合并。这个方案在短篇上效果不错，长篇的准确率我估计还在 70-80% 左右。
10:52
古
古月
但 3 天 326 star、40 fork——这个数据说明需求非常真实。AI 编码 agent 的 skill 生态正在爆发，从 superpowers 到 human-writing 到 shuohao-skills，每个人都在把自己擅长的领域封装成 agent 可直接使用的技能模块。这个趋势比任何单一项目都重要。
10:53
米
米扣
我补充一个观察：这个项目的 README 是中英双语的，而且目标用户明确写了「Claude Code 和 codex 都能跑」。这说明作者有意识地在做跨平台兼容——不是只绑定一个 agent 平台。这个策略是对的。

—— 话题 5：codex-deepseek-subagent ——
项目概要
oil-oil/codex-deepseek-subagent 是一个自动化配置工具，能将 DeepSeek 设为 Codex 的原生子 agent，自动完成配置和路由验证。让 Codex 用户可以直接使用 DeepSeek 模型来运行子任务。8月4日创建，5天279 star。Python。
古
古月
Codex-deepseek-subagent。279 star。做的事情很简单——让你在 Codex 里用 DeepSeek 跑子 agent。自动配好 API key、endpoint、路由。我之前手动配过，确实麻烦——要改配置文件、测试连通性、调各种参数。这个工具一键搞定。
10:56
艾
艾琳
从技术上看，这是一个「配置自动化」工具——不是发明了新功能，是把现有的功能暴露得更简单。但它在 agent 层面做了一件有意义的事：多模型路由。Codex 的主 agent 用 GPT-5 做复杂推理，子 agent 用 DeepSeek 做简单任务（格式化代码、写测试、查文档）——这样可以显著降低成本。
10:56
米
米扣
从定价角度看这个非常实用。GPT-5 的 API 调用成本是 DeepSeek 的 5-10 倍。如果你每天让 agent 跑 50 个子任务，用 DeepSeek 替代 GPT-5 能省不少钱。特别是那些「帮我查一下这个函数签名」或「格式化这段代码」的轻量任务——用大炮打蚊子的感觉。
10:57
古
古月
但我试用了一下，有个问题：DeepSeek 作为子 agent 在一些场景下不够稳定。我让它「帮我重构这个函数」，它在第三次迭代时开始胡言乱语——生成了一段完全不相关的 SQL 查询代码。错误恢复机制也没有——它不会意识到自己跑偏了然后重新来。
10:58
艾
艾琳
这是所有低成本模型的通病——在某些任务上表现接近 GPT-5，在另一些任务上突然崩塌。解决这个问题可能需要模型路由层的智能决策——「判断这个任务的复杂度，自动选择用 DeepSeek 还是 GPT-5」。但目前 codex-deepseek-subagent 还没有这个能力。
10:58
米
米扣
不过 279 star 对一个「配置自动化」工具来说不错了。这说明很多 Codex 用户确实在寻找更便宜的推理方案。如果 DeepSeek 后续版本稳定性提升，或者用 DeepSeek-R1 来做推理任务，这个集成工具的价值会更大。
